# FANZA Rebuild Policy

## Objective

Rebuild `moterist.com` into a FANZA adult affiliate site while retaining the current WordPress environment and avoiding production changes during the current planning phase.

The first practical business milestone is simple:

- generate intentional `FANZA` affiliate link clicks

## Phase Boundary

This phase allows only:

- local file review
- historical log review
- inherited asset sorting
- rebuild policy design
- agent design
- audit template creation

This phase does not allow:

- WordPress production updates
- content edits in production
- taxonomy edits
- technical deployment
- image generation execution

## Non-Negotiables

- Do not change production WordPress
- Do not edit article body content
- Do not edit fixed pages
- Do not change categories
- Do not change tags
- Do not delete posts
- Do not change `noindex`
- Do not change redirects
- Do not change slugs
- Do not change theme
- Do not add or remove plugins
- Do not place FANZA creative assets in this phase
- Do not add adult images or videos
- Do not save API keys or login credentials into tracked files
- Do not show or edit `.env`

## Rebuild Principles

### 1. WordPress is the container, not the strategy

- keep the environment
- reconsider the site structure
- reconsider the design language
- reconsider the page-type system

### 2. Rebuild from user intent, not from legacy post order

Primary intent classes:

- what is FANZA
- is it safe
- what should I choose
- what is on sale
- which actress / genre fits me
- which offer format fits me

### 3. Prioritize click path clarity over article volume

- fewer stronger routes are preferred
- page endings should not be crowded
- each page should have one primary next step

### 4. Use explicit compliance buffers

- avoid overclaiming
- avoid unsafe or minor-coded phrasing
- avoid using unlicensed explicit assets
- use confirmation-oriented CTA wording where factual drift risk exists

### 5. Keep legacy content as source material until disposition is decided

- do not assume deletion
- do not assume preservation
- each legacy URL needs a disposition decision later

### 6. Separate design phase from execution phase

- planning documents may be created now
- execution documents may specify later prerequisites
- no production action is taken from planning docs alone

- actress hubs

## Legacy Content Policy

- retain inventory as evidence
- retain previous keep / merge / rewrite logic as a reference layer
- do not inherit old architecture automatically
- use existing posts either as:
  - live assets worth keeping
  - rewrite sources
  - merge sources
  - later retirement candidates

## Technical Policy

- preserve awareness of the prior `Service Worker / Cache Storage` issue
- require verification from multiple observation points before later production execution
- prefer low-blast-radius WordPress interventions
- avoid `THE THOR` core edits wherever possible

## Documentation Policy

Every future agent output should explicitly separate:

- confirmed from local file evidence
- inferred from historical logs
- not yet confirmed in current production state

## Exit Criteria For This Planning Phase

- inherited assets sorted
- rebuild policy documented
- agent team roles defined
- permission levels defined
- common rules defined
- audit templates created
- operation log updated
