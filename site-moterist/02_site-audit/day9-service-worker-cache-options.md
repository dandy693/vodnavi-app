# Day 9 Service Worker Cache Options

## 現状の問題

Day 8 の本番修正後、`1106` / `994` は管理画面保存済み本文、サーバー側 curl、Service Worker をブロックした新規ブラウザコンテキストでは新HTMLが返っていた。一方で、通常ブラウザでは旧HTMLが残るケースがあり、更新確認を誤判定しやすい状態だった。

## Service Workerが旧HTMLを残す仕組み

- `serviceWorker.js` が存在する
- fetch イベントで HTML レスポンスを Cache Storage に保存・再利用する実装が確認されている
- THE THOR 側で Service Worker が登録されている
- Chrome DevTools 上で `moterist.com` の Service Worker と `cache-v...` の Cache Storage が確認されている
- このため、サーバー上の公開HTMLが更新されていても、既存ブラウザが古い HTML をローカルキャッシュから返す可能性がある

## 対応案A: PWA停止

内容:

- THE THOR の PWA / Service Worker 登録自体を止める

メリット:

- 問題の根本を最も単純に断てる
- 記事HTMLの stale 表示リスクを大きく下げやすい
- 更新確認運用がシンプルになる

リスク:

- PWA 機能全体が止まる
- オフライン性や再訪時の高速表示メリットが失われる
- テーマ設定や登録処理の停止箇所を誤ると副作用確認が必要

## 対応案B: 記事HTMLをService Workerキャッシュ対象から外す

内容:

- HTML 文書は Cache Storage に保存せず、画像・CSS・JS 等の静的資産だけを Service Worker 管理対象にする

メリット:

- 記事更新時の旧HTML残存を直接回避しやすい
- PWA の静的資産キャッシュ利点は残しやすい
- 公開記事確認フローと相性がよい

リスク:

- Service Worker 実装の対象切り分けを誤ると、必要なキャッシュまで外す可能性がある
- THE THOR の実装と整合しない変更をすると、テーマ更新で管理が複雑になる

## 対応案C: navigation requestをnetwork-firstへ変更

内容:

- navigation request は常にネットワーク取得を優先し、失敗時のみキャッシュを返す

メリット:

- 更新直後でも新HTMLを取得しやすい
- HTML キャッシュを完全停止しなくても stale 表示を減らせる
- オフライン時のフォールバックを残しやすい

リスク:

- ネットワーク不調時の挙動設計が必要
- 実装を誤ると、ページ遷移時の体感速度やエラー時挙動に影響する
- テーマ更新との整合管理が必要

## 対応案D: 確認運用だけで対応する

内容:

- 実装変更はせず、更新確認時に `Service Worker 無効化`、`新規ブラウザコンテキスト`、`サーバーcurl確認` を必須運用にする

メリット:

- 本番コードを触らずに始められる
- テーマ更新や実装互換性の問題がない
- 緊急性が低い場合の暫定運用として安全

リスク:

- ユーザー側の旧表示リスクは残る
- 人間確認の手順負担が増える
- 恒久対応にはならない

## 各案のメリット

- A:
  - 問題源を広く止められる
- B:
  - 記事更新の stale 表示を直接減らしやすい
- C:
  - HTML stale 表示を抑えつつ PWA の一部利点を残しやすい
- D:
  - もっとも安全に即日運用できる

## 各案のリスク

- A:
  - PWA 利点の喪失
- B:
  - 対象除外の実装ミス
- C:
  - network-first の挙動設計不備
- D:
  - ユーザー影響は残存

## 推奨案

推奨は `B + D` の組み合わせ。

- 恒久対応としては、記事HTMLを Service Worker キャッシュ対象から外す案を第一候補とする
- 反映前後の運用としては、Service Worker 無効化 / 新規ブラウザコンテキスト / サーバーcurl確認を継続する

理由:

- moterist.com は公開記事の更新確認精度が重要で、HTML stale を残す利点が小さい
- PWA 全停止より影響範囲を絞りやすい
- network-first だけよりも、HTML 自体を対象外にするほうが意図が明確

## 本番反映前の確認項目

- THE THOR 側で Service Worker をどこで登録しているか
- HTML が現行でどの条件で Cache Storage に入るか
- 子テーマまたは MU プラグインで安全に上書きできるか
- テーマ更新時に本体差分へ依存しないか
- 変更後に以下が維持されるか
  - CSS / JS / 画像の読み込み
  - スマホ表示
  - 通常URLの即時反映確認
  - PWA 利用時の最低限の表示安定性

## ロールバック方針

- 現行の Service Worker 登録条件とキャッシュ戦略を事前に記録する
- 変更は 1 論点ずつ反映する
- 問題が出た場合は、直前の Service Worker 登録・キャッシュ条件に戻す
- ロールバック後は Cache Storage バージョンと既存登録状態の整合確認を行う

## やってはいけないこと

- いきなり `serviceWorker.js` を削除する
- THE THOR 本体を直接編集する
- キャッシュ削除だけで恒久対応扱いにする
