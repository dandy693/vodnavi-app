## D1: 旧作worksアーカイブサイトマップ

### 現状構成（実測）
- `src/app/sitemap.ts` 単一ファイル → `/sitemap.xml`（`export const revalidate = 3600`）。robots.ts が `sitemap: /sitemap.xml` を宣言
- 収録: FANZA_FLOORS 4フロア（videoa / amateur※apiFloor=videoa+素人keyword / anime / nikkatsu）× PAGES_PER_FLOOR=4 × 100件 = **最大1,600 works枠**（amateur⊂videoaの重複除去で実質やや減）、`sort: "date"` = **新作が旧作を押し出す回転式**
- 帰結: 一度掲載→押し出された旧作は sitemap から永久に消える。7/9サンプル調査: 旧作10件中 sitemap収録1・完全孤立4（内部リンクも痩せ）

### 対象URL群の抽出条件
「**過去に sitemap 生成時のフェッチで観測された全 works** − 現行 sitemap 掲載中の works」。実装上は観測時点で永続記録し（下記）、アーカイブ側は記録全量から現行分を除外して出力（重複掲載でも Google 側は無害だが、清潔化のため除外）

### 分割構成案（推奨A: 追加サイトマップ方式）
1. **Supabase 累積テーブル** `sitemap_works_archive`（`content_id` PK / `floor_code` / `released_at` / `first_seen_at` / `last_seen_at`）。既存 sitemap.ts の works 走査ループ内で **fire-and-forget の一括 upsert**（await しない・失敗無視 → 本体 sitemap 生成に遅延/障害を波及させない）。Supabase Option B の service-role 配線（本番疎通確認済 2026-06-28）を再利用、追加 FANZA API コール **0**
2. **新ルート `/sitemap-archive.xml`**（route handler・revalidate 3600）: Supabase のみを読む（FANZA API 0コール）。Supabase 障害時は空 sitemap を返す graceful 実装（getPublishedArticleSlugs と同型）→ 本体 `/sitemap.xml` は完全無影響
3. **robots.ts の sitemap 宣言を配列化**して両方を宣言（`MetadataRoute.Robots` は `string[]` 対応）→ クローラ自動発見。GSC への手動登録は不要（HUMAN が追加登録すればカバレッジレポートの分離観測が可能になる、推奨）

### 既存 sitemap.xml との関係
既存 `/sitemap.xml` は**一切変更しない**（URL・収録構成・revalidate 3600 とも不変）。変更は「書込みフックの追加」のみで出力に影響なし。→ GSC 登録済み sitemap の再クロール断絶リスクなし

### 却下した代替案
- **B: `generateSitemaps()` によるインデックス化** — `/sitemap.xml` の URL 構造が変わり GSC 再登録+検出リセットのリスク。棄却
- **C: PAGES_PER_FLOOR 増加** — FANZA API 呼数が恒常増（スロットル誘発）。R1（API負荷起因の障害再発防止）と正面衝突。棄却

### 期待効果
- 旧作 works ~800件（増加中）が恒久的に sitemap 経由でクロール対象として明示される → クロールバジェットの配分先ヒント+canonical 選択の安定化
- 「検出-未登録」→「クロール済み」→「登録」への転換率が**アーカイブ sitemap 単位で計測可能**になる（D3=ハブpagination要否の再判断に必要な前提データ。CSO裁定 2026-07-09: D3はD1効果測定後に再判断）
- 注: sitemap 掲載はインデックス保証ではない。内部リンク面の補完は M-07 フッターリンククラウド（浸透済）が既に担う

### リスクと緩和
- **廃売 content_id の404蓄積**: works 詳細は API cid 逆引きのため大半生存（7/9サンプル 10/10生存）。緩和: `last_seen_at` から **180日** で自動除外する鮮度キャップ + 週次定常の GSC 404 監視に「アーカイブ由来」の観点を追加
- **sitemap サイズ**: 現規模は数千件 = 1ファイル50,000件上限に遠い。将来超過時のみ分割（設計に含めない）
- **Supabase 障害**: 上記のとおり graceful（空出力）で本体無影響

## D2: /concierge?source= の canonical 統合

### 結論（物理検証済み）: **既に実装済み・追加変更不要 = 0デプロイ**
- 本番確認（2026-07-14 curl）: `https://app.vodnavi.jp/concierge?source=moterist` が `<link rel="canonical" href="https://app.vodnavi.jp/concierge"/>` + `<meta name="robots" content="index, follow"/>` を返す
- 実装箇所: `src/app/concierge/layout.tsx:10` `alternates: { canonical: absoluteUrl("/concierge") }` — **セグメント metadata のためクエリ全変種（source/intent/cids/seed_cid）に適用される**。導入は bc72ddc（現行構造の初期から）
- FACT_GOVERNANCE §2（noindex 厳禁・self-canonical consolidation）に完全合致

### source= バリエーション実在庫
- コード定義（`src/lib/concierge/sources.ts`）: **7種** — `default` / `moterist` / `brand` / `app_detail` / `sns_x` / `app_3tap` / `brand_pilot_001`（未知値は default へフォールバック=無限変種は発生しない）
- GSC 実在庫: 2026-07-09 DOM抽出分類で `/concierge?source=` **63件**（param変種69の内訳、その他 `/?floor=` 1・favicon/OG変種5）。個別URL全列挙の再取得は GSC エクスポート（HUMAN）で可能だが、実装済み確認により優先度低

### 方式比較（canonical メタタグ vs リダイレクト）
**リダイレクトは不採用**。`source=` は (a) GA4 流入識別（`?source=moterist` = moterist 凍結面の識別子・FACT_GOVERNANCE §2）(b) コンシェルジュ挨拶/システムプロンプト分岐（resolveConciergeSource）の**機能パラメータ**であり、301でクエリを剥がすと計測とUXの両方が壊れる。メタタグ self-canonical（現行）が正

### GSC残存低下との干渉評価（指示要求事項）
**干渉ゼロ**。変更を行わないため canonical 反映ラグも新規クロール需要も発生せず、回復途上の検索露出・7/21評価の計測（works週次AU）に対する影響は無い。残る63件の「クロール済み-未登録」は Google 側 consolidation の完了待ち（数週間スケールの受動プロセス）で、/concierge へ評価集約される設計どおりの挙動
