## 1. 案A（Airtable Automation による通知）

### 実装すると、こうなる（CSO 案の読み替え）

```
トリガー : At scheduled time（cron） 例: 毎週木 10:00 JST／または毎日 10:00 JST
アクション: ① Find records
              テーブル posts / 条件: ステータス = 承認済 AND 予約日時 is after today
            ② Conditional action group（件数 < 閾値 のとき）
            ③ Send an email（宛先は既存と同じ moterist.com@gmail.com）
```

| 観点 | 評価 |
|---|---|
| 検知の確実性 | **高い**。セッションの有無に依存せず、機械が定時に評価する |
| 実装コスト | **中**。トリガ読み替え＋Find records＋条件分岐の3要素。既存「エラー通知」は sendEmail 1ノードのみで、**参考にはなるが同型ではない** |
| 未確認リスク | ①**条件分岐（Conditional action group）が現プランで保存できるか未確認** ②**自動化の実行回数上限が未確認**（プラン依存）。毎日実行なら月約30回、毎週なら月約4回 |
| 実績リスク | **既存オートメーションは本番発火の実績が 0**（事実3）。「同型だから動く」とは言えず、**作成後に Test automation での検証が必須** |
| 本質的な限界 | **通知は「気づき」までしか担保しない**。メールを見て人が補充タスクを起票しないと在庫は増えない |
| 閾値の妥当性 | CSO 案の **3件は現行運用（2件/日）で 1.5 日分**。運用則「木曜に翌週月〜水を確保」＝**3日分=6件**と整合させるなら **閾値は6件**が対応する |

**条件分岐が使えない場合の代替**: 条件分岐なしで「毎週木 10:00 に在庫件数を必ずメールする定期レポート型」にすれば、機能制限を回避できる（週4回/月・常に届くが、木曜チェックの起点にはなる）。

## 5. 推奨（CTO 見解）

**案A（cron 読み替え版）と案B の併用を推奨する。ただし案A単独では不十分**という前提で組む。

理由は次の3点に集約される。

1. **今回の事象は「エラー」ではなく「不在」だった。** 既存の通知設計（ステータス=エラー）は原理的にこれを検知できない。**機械的な定時チェックを1つ足すこと自体は、失敗モードに直接対応している**
2. **案Bだけでは同じ失敗を繰り返す蓋然性が高い。** 運用則「木曜に翌週月〜水を確保」は**既に台帳に存在した上で今回の枯渇が起きた**。追記だけを対策とするのは、原因に対する手当てになっていない
3. **案Aだけでも足りない。** 通知は気づきまでしか担保せず、補充作業自体は人／CTO が行う。**通知 → TASK_BOARD 起票 → 補充**の経路を案Bで用意して初めて閉じる

### 実装するなら、この順で

| 段階 | 内容 | 承認要否 |
|---|---|---|
| 1 | **案B を先に実施**（コストゼロ・設定変更なし）。ただし TASK_BOARD 本文への追記だけでなく、**毎セッション自動ロードされる文書（`CLAUDE.md` または `FACT_GOVERNANCE.md`）に1行**を入れて埋没を防ぐ | CSO 承認 |
| 2 | **案A の前提2点を確認**（① Conditional action group が保存できるか ② 自動化の実行回数上限） | 閲覧のみで可 |
| 3 | 前提が満たされれば **案A を cron 型で作成 → Test automation で発火検証**。満たされなければ**条件分岐なしの週次レポート型**へ縮退 | **CSO 承認必須**（設定変更） |

### 併せて提案する調整（実装時）

- **閾値は 3件ではなく 6件**（運用則「翌週月〜水＝3日分」×2件/日と整合させる）
- **実行は毎週木 10:00 JST**（既存の運用則と同じ曜日に合わせ、リマインドとチェックを1点に集約する）
- 通知先は既存と同じ `moterist.com@gmail.com`（新規の宛先を増やさない）
