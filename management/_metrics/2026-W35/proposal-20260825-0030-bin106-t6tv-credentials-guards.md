### A-4. 自動化率の検算（A(4)）

#### (1) §11-2 の数値の内部整合

| 段階 | 台帳の値 | 週あたり件数 | **逆算した分母** |

## B. `ai_proposer` 資格情報の配置場所（起案）

**【非交渉の制約を確認した】資格情報の値そのものは生成・取得・記録しない。本項は「どこに・どの名前で・どの保護設定で置くか」の枠のみを起案する。値の設定は CSO が直接行う。**

### B-0. 【設計上の分岐点】置くべきものは「鍵」ではなく **JWT** である

**§12 の実測**: **`ai_proposer` は `nologin` のため Postgres へ直接接続できない。** **PostgREST が JWT の `role` クレームで `set local role` する経路が前提**であり、**必要なのは署名済み JWT である。**

**ここで重大な分岐がある**:

| 置くもの | 権限の広さ | 判定 |
|---|---|---|
| **Supabase の JWT シークレット（署名鍵）** | **任意のロールの JWT を発行できる＝`service_role` も名乗れる。** **`SUPABASE_SERVICE_ROLE_KEY` より広い** | **採らない。** 三層防御の意味が消える |
| **事前発行した長寿命の `ai_proposer` JWT** | **`ai_proposer` に固定。INSERT のみ・RLS `with check` とトリガ3種の下にある** | **こちらを採る** |

- **【厳守】署名鍵を置く案は比較表に載せない。** **§12 の三層（GRANT なし / RLS `with check` / トリガ3種）は「AI 提案バッチのプロセスが `live` に到達する経路が存在しない」ことを保証するが、__署名鍵を持てばその前提ごと崩れる__。**
- **帰結として、失効・更新の運用が必要になる**（JWT には `exp` がある）。**下の比較表はこれを「運用手間」に織り込んである。**

### B-1. 配置場所の比較

**前提として、B2②-b の提案バッチを__どこで走らせるか__で選択肢が変わる。**

### B-3. 【厳守】この起案が解決しないこと

- **JWT の失効。** **`exp` が来れば再設定が必要で、そのたびに HUMAN 介在（分類B）が1件増える。** **有効期限をどれだけ長く取るかは CSO の判断事項**（長いほど運用は楽だが、漏洩時の影響期間が延びる）。
- **§12 の限界そのもの。** **Supabase の service role は RLS を迂回する。** **レンダラを実装した時点で `getServiceRoleClient()` を通ることになり、同じ限界が生じる**（§12 の追記どおり）。**本起案は「提案バッチの資格情報をどこに置くか」だけを扱っており、その限界には触れていない。**
- **`ai_proposer` には SELECT ポリシーが無い**（§12 の実測）。**したがって §10 の「INSERT 後に読み戻して検算する」は、この鍵しか持たないプロセスでは実行できない。** **検算は別経路（`link_approver` か service role）で行う必要がある。** **どちらを使うかは未裁定。**

## C. §13-8 恒久ガード3案の具体化（起案・**実装しない**）

### C-0. 記号の定義

| 記号 | 意味 |
|---|---|

| **R** | 女優名を解決できた行数 |
| **U** | 解決失敗行数（`U = T − R`） |

### C-1. 3案の比較表

| | **案A（絶対件数）** | **案B（相対比較）** | **案C（解決失敗率）** |
|---|---|---|---|
| **判定式** | **`N_new < A_MIN` なら拒否** | **`N_new < N_cur × B_RATIO` なら拒否** | **`U / T > C_MAX` なら拒否** |

### C-2. 【定量化】部分故障をどれだけ通してしまうか（第105便 C の注記の数値化）

**仮定**: **失われる女優数は失敗した行数に比例する**（`N_new ≈ N_cur × (1 − U/T)`）。**`N_cur = 71` / `T = 24` を用いる。**

| **`U/T`（失敗率）** | `N_new`（推定） | **案A**（`<10`） | **案B**（`<35.5`） | **案C**（`>10%`） | **静かに消える女優数** |
|---|---|---|---|---|---|
| 0% | 71 | 通す | 通す | 通す | 0 |
| **10%** | 64 | 通す | 通す | **通す（境界）** | **7** |
| **20%** | 57 | **通す** | **通す** | **拒否** | 14 |
| **30%** | 50 | **通す** | **通す** | **拒否** | 21 |
| **50%** | 36 | **通す** | **通す（境界）** | **拒否** | 35 |
| 60% | 28 | **通す** | 拒否 | 拒否 | 43 |
| 90% | 7 | 拒否 | 拒否 | 拒否 | 64 |
| **100%（8/24 の実測）** | **0** | **拒否** | **拒否** | **拒否** | 71 |

**読み取れること**:

- **案A は部分故障に対してほぼ無力である。** **86% の行が失敗しても通す。** **「全滅だけを止める最後の砦」としてしか機能しない。**
- **案B は 50% までの部分故障を通す。** **35名が静かに消えても書き込まれる。**
- **案C が最も早く止まる。** **20% の失敗で拒否する。**
- **【厳守】どの案も 10% 前後の部分故障は通す。** **したがって「ガードを入れたから dry-run は不要」とはならない**（§13-8 の注記どおり）。

### C-3. **推奨：案C を主、案A を最後の砦として併用**

**判定式（案）**:

```
if (U / T > C_MAX) reject;          // 主: 原因に最も近い指標で早く止める
if (N_new < A_MIN) reject;          // 従: T 自体が異常に小さい場合の最後の砦
```

| 推奨の根拠 | 内容 |
|---|---|
| **案C は原因を直接見ている** | **失敗モードは「API が解決を返さない」であり、`U/T` はそれをそのまま測る。** **件数の増減（案A・案B）は結果の指標であり、原因との間に「1作品あたりの女優数」という交絡が挟まる。** |
| **案A を併用する理由** | **`T` 自体が 0 か極端に小さい場合、`U/T` は 0/0 または不安定になる。** **そのとき案C は判定できない。** **案A は `N_new` の絶対値だけを見るので、この穴を塞ぐ。** |
| **案B を採らない理由** | **現行表を基準にするため、__現行表が既に壊れている場合に基準ごと壊れる__。** **本ガードは「表が壊れるのを防ぐ」ものなので、壊れた表を基準にする設計は目的と矛盾する。** |

### C-4. 【厳守】閾値の値は本起案では確定できない

- **`C_MAX = 0.10` / `A_MIN = 10` は__仮の値__である。** **根拠となる実測（平常時の `U/T` の分布）を持っていない。**
- **B8 のような恒久的な取得不能がどれだけ積み上がっているかも未測定である。** **これが平常時の `U/T` の下限を押し上げる。**
- **【推奨する進め方】まず `U` / `T` / `N_new` / `N_cur` を__ログに出すだけ__の変更を入れ、数回の再生成で分布を見てから閾値を決める。** **拒否は分布が見えてから有効化する。**
- **これは「ガードを先送りする」意味ではない。** **閾値を勘で決めると、誤検知で運用が止まるか、見逃しで表が壊れるかのどちらかになる。**
