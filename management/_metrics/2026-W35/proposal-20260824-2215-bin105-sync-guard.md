# 起案 — `sync-actress-table.mjs` に「解決件数の下限ガード」を入れる

**起案日**: 2026-08-24（第105便 C(2)）
**状態**: **起案のみ。実装は 9/12 以降の CSO 裁定待ち。本便では実装していない。**
**根拠**: `FACT_GOVERNANCE` §13-8（2026-08-24 実測）

> **【厳守】本書は案である。CTO は採否を決定しない。**

---

## 1. 何を防ぐガードか

**`ACTRESS_LAST_POSTED` の再生成中に FANZA API が停止していると、女優名を1件も解決できず、生成される表が空になる。**
**その状態で `--write` を実行すると `g12`（30日以内の女優の再登場禁止）が全通しになる。**

**2026-08-24 の実測では dry-run を先に行ったため書き込まなかった。** **しかし現状、`--write` を直接実行すれば何の抵抗もなく表が空になる。**

---

## 2. 案（3つ）

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **案A: 絶対件数の下限** | **解決できた女優が N 人未満なら `--write` でも書き込まない**（例 N=10） | 実装が最も単純。API 全停止（0件）は確実に止まる | **閾値の根拠が無い。** 運用初期や大量削除時に誤って止めうる |
| **案B: 現行表との相対比較** | **現行 `ACTRESS_LAST_POSTED` の件数に対し、生成結果が X% 未満なら書き込まない**（例 X=50%） | **「急に大きく減った」という異常の形に直接対応する。** 閾値が相対なので運用規模に追随する | 現行表が既に壊れている場合、壊れた値を基準にしてしまう |
| **案C: 解決失敗率で判定** | **`unresolved`（FANZA から取得できなかった行）が全対象の Y% を超えたら書き込まない**（例 Y=20%） | **原因（API 停止）に最も近い指標を見る。** 件数の増減とは独立 | 個別作品の恒久的な取得不能（B8 のような 404 化）が積み上がると、正常時でも閾値に近づきうる |

**併用も可能**（例: 案C を主、案A を最後の砦とする）。

---

## 3. 各案に共通して必要なもの

- **`--force` のような回避手段を用意するか**は別途の判断。**用意するなら、回避したことがログに残ること。**
- **拒否したときの終了コードを非0にする**（呼び出し側が気づけるように）。
- **拒否理由を「何件中何件が解決できなかったか」で出す**（閾値だけを出さない）。

---

## 4. 【厳守】このガードが解決しないこと

- **API が「部分的に」壊れている場合**——一部の `content_id` だけが取得できない状態では、**どの案でも通ってしまいうる。** **その場合、表からは一部の女優だけが静かに消える。**
- **したがって、ガードを入れても dry-run 先行の手順（§13-8）は不要にならない。** **ガードは「最悪の事故を止める」ものであり、「確認を省略してよい」という意味ではない。**

---

## 5. 判断が必要な点

1. **どの案を採るか**（A / B / C / 併用 / 採らない）
2. **閾値の値**（採る案に応じて N / X / Y）
3. **`--force` を用意するか**
4. **実装時期**（9/12 以降のどこか）

**【厳守】CTO は推奨しない。** **閾値の根拠となる実測（過去の再生成での解決件数の分布）を持っていないため。** **必要なら、数回の再生成で件数を記録してから決めるほうが確実である。**
