**根拠**: `FACT_GOVERNANCE` §12（実測 2026-08-11 / 訂正 2026-08-18・第72便）

> **【厳守】本書は案である。CTO は採否を決定しない。**

## 0. 何が問題か（**§12 の実測の再掲**）

| 実測 | 出典 |
|---|---|
| **`internal_links` の SELECT ポリシーは `approver_select`（`link_approver`）ただ1つ。`ai_proposer` には SELECT ポリシーが存在しない** | §12（実測 2026-08-18） |
| `ai_proposer` の GRANT は **テーブル INSERT のみ**（`nologin` / `bypassrls=false`） | §12（実測 2026-08-11） |
| `link_approver` は **SELECT** + **列単位 UPDATE（`status` / `approved_at` / `approved_by`）のみ** | 同上 |

**帰結**: **§10 の「書き込み後に対象側の値を読み戻して確認する」が、`ai_proposer` の資格情報しか持たないプロセスでは実行できない。**

**【厳守】これは設計の帰結であって欠陥ではない**（§12 が明記）。**問われているのは「検算をどの経路で行うか」であって「`ai_proposer` の権限が足りない」ではない。**

### 検算が要る理由（**省略できない**）

- **§10 は「書き込み系ツールが成功を返しても、書き込まれた証拠にはならない」**を運用則として定めている。**PostgREST が 201 を返しても、行が意図どおり入った証拠にはならない。**
- **特に `internal_links` は `guard_ai_proposal()` トリガ3種と `chk_no_self_link` が働く。** **拒否は例外として返るが、`origin` / `status` / `approved_at` / `approved_by` が意図どおりの値で入ったかは読まなければ分からない。**

## 1. 比較（**2案 + 実装しない案**）

| 軸 | **案1: `ai_proposer` に SELECT ポリシーを追加** | **案2: 検算専用の別経路（`link_approver` の SELECT を流用）** | （参考）案3: service role で読む |
|---|---|---|---|
| **権限の最小性** | **INSERT + SELECT の2権限になる。** ポリシーを `origin='ai' and status='proposed'` に絞れば**自分が入れうる行しか見えない**。**承認済み・掲出中の行は見えないまま** | **`link_approver` は既に SELECT を持つ＝新しい権限を1つも増やさない。** ただし**同じプロセスが `status` を UPDATE できる鍵を持つことになる** | **最小性が最も低い。** service role は**全テーブル・全操作**が可能 |
| **§12（RLS 迂回）との整合** | **整合する。** `ai_proposer` は `bypassrls=false` のままで、**RLS の枠内で読む** | **整合する**（`link_approver` も `bypassrls=false`）。**ただし §12 の三層のうち「GRANT を出さない」が、検算プロセスに対して崩れる** | **整合しない。** **service role は RLS を迂回する**（§12 の追記）。**三層防御の前提が崩れる** |
| **運用手間** | **ポリシー1本の追加。資格情報は増えない**（JWT 1本のまま） | **JWT が2本になる**（`ai_proposer` + `link_approver`）。**失効・更新の対象が2倍**（§12 の B 起案が挙げた分類B の増加が2件になる） | 既存の `getServiceRoleClient()` を流用でき**手間は最小** |
| **失敗モードの検出可能性** | **INSERT 直後に同一プロセスが読める＝§10 の形そのもの。** ポリシーの絞り込みが強すぎて0件になった場合、**「書けていない」と「見えていない」を区別できない**（→ §2 の緩和策） | **同左（検出力は同じ）。** さらに `link_approver` は**全 `status` を見られるため、`live` まで含めた最終確認ができる** | 何でも読めるため検出力は最大 |
| **最も重い副作用** | **`ai_proposer` が読める範囲が増える。** ただし**書ける範囲は1ミリも増えない**（INSERT の RLS `with check` は不変） | **【最重要】検算プロセスが `link_approver` の鍵を持つと、§12 が「運用構造による担保」と明記した前提が崩れる**——**「提案バッチのプロセスに `link_approver` の鍵を渡さないこと」が、人間の承認を担保する唯一の手段である**（§12 原文） | **`status='live'` を直接書ける主体が増える**（§12 の追記が名指しで警告） |

### 【決定的】案2 は §12 の原文と正面から衝突する

**§12 原文**:

> **DB は「人間が実際に承認したこと」を検証できない。** その担保は**運用構造**による——**提案バッチのプロセスに `link_approver` の鍵を渡さないこと**、および **LLM は資格情報を持たず「JSON を返す関数」であって DB のアクターではないこと**。

- **案2 は「検算専用」と限定しても、__同じ実行環境（Vercel のランタイム）に `link_approver` の鍵が置かれる__ことを意味する。**
- **Vercel の環境変数はプロセス単位で分離されない。** **`SUPABASE_AI_PROPOSER_JWT` を読むコードと `SUPABASE_LINK_APPROVER_JWT` を読むコードは、同じ `process.env` を共有する。**
- **したがって「検算にしか使わない」は__コードの約束__であって、__構造的な保証__ではない。** **これは §13 が X 投稿について記録した「スクリプトを書き換えれば `承認済` を直接書ける」一層防御と同じ強度に落ちるということである。**
- **B2②-b の三層防御は「AI 提案バッチのプロセスが `live` に到達する経路が存在しないこと」を保証するもので、その第一層がまさに「GRANT を出さない」である。** **案2 はこの第一層を、検算のために自ら開ける。**

## 2. 推奨案 — **案1（`ai_proposer` に SELECT ポリシーを追加）**

| 推奨の根拠 | 内容 |
|---|---|
| **三層防御を崩さない** | **`ai_proposer` の書き込み権限は変わらない**（INSERT のみ・RLS `with check`・トリガ3種）。**増えるのは読み取りだけで、`live` への経路は依然として存在しない。** |
| **§12 の運用構造の前提を守る** | **`link_approver` の鍵は提案バッチのプロセスに渡らないまま**でいられる。**案2 はここを開ける。** |
| **資格情報が増えない** | JWT は 1本のまま。**失効・更新の運用（分類B）が2倍にならない。** |
| **§10 の形に一致する** | **同一プロセスが「書いた直後に読む」**。別経路だと、**書いた時点と読んだ時点の間に別の主体が触れていないことを言えない。** |

### 推奨するポリシーの形（**値ではなく枠**）

```
-- 読めるのは「AI が入れた、まだ提案段階の行」だけに絞る
create policy proposer_select_own on public.internal_links
  for select to ai_proposer
  using (origin = 'ai' and status = 'proposed');
```

- **`approved` / `live` / `retired` は見えない。** **AI は自分の提案の着地だけを確認でき、承認の結果は見えない。**
- **【厳守】この絞り込みには副作用がある**——**「INSERT が拒否された」と「INSERT はされたが `status` が既に動かされていて見えない」を区別できない。** **後者は現実には起こりにくい（承認は人間の操作）が、区別できないことは記録しておく。**
- **緩和**: **INSERT の応答が返した `id` を使って読む**（`select ... where id = $1`）。**0件なら「その id の行は `origin='ai' and status='proposed'` ではない」まで言え、「そもそも書けていない」との区別が付く。**

### 【厳守】この案が解決しないこと

- **§12 の service role の限界は変わらない。** **レンダラを実装した時点で `getServiceRoleClient()` を通ることになり、RLS 迂回の経路は残る。** **本案は提案バッチの検算だけを扱う。**
- **「人間が実際に承認したこと」の検証にはならない。** **§12 のとおり DB はこれを検証できない。** **本案が可能にするのは「AI が入れた行が意図どおり入ったか」の確認だけである。**
- **ポリシー追加は DDL であり、`internal_links` に対する変更である。** **実施時期は B2②-b 本体の着手時期に従う。**
