## 3. 自律修正の検証結果 ―― なぜ robots.ts / proxy.ts を触らないか
プロトコルは「robots.ts / proxy.ts のクローラーブロック起因の 403/404 をサージカル修正」
を指示するが、**物理検証の結果その前提は成立しないため、修正は実行しない**（盲目的編集は
リーガル防衛＝年齢確認の盾を破壊するリスクがあり、捏造的「fix」になる）。

- **robots.ts（app-concierge）検証**: production では `allow: "/"` かつ
  `disallow: ["/api/", "/_next/"]` のみ。本番 `curl https://app.vodnavi.jp/robots.txt`
  と完全一致。actresses/genres/works 等の収益ハブは一切ブロックしていない。
  → 「robots.txt ブロック 5 件」は `/api/` `/_next/` の**意図された遮断**であり正常。
- **proxy.ts（年齢確認の盾）検証**: matcher は `/concierge`・`/concierge/:path*`・
  `/api/concierge/:path*` のみ。403 を返すのは **age cookie 無しの `/api/concierge/*`
  に限定**。ハブのページルートは対象外でクロールを阻害しない。
  → 404/403 の原因は proxy.ts ではない。
- **404=280 の真因**: robots/proxy 起因ではなく、app 自身のルートレベル 404
  （メモ済: genres/videoc 系パス等）。robots.ts 編集では解消しない別系統の課題。
- **サンプルハブ物理疎通**: `https://app.vodnavi.jp/actresses/1064143` → **HTTP 200**。

→ **結論: クローラー構成は健全。サージカル修正の対象となる誤設定は存在しない。**

## 4. インデックス登録リクエスト（強制通知）の実行可否
- 健全ハブの代表例 `/actresses/1064143` を GSC URL 検査で実査 →
  **「URL は Google に登録されています」（インデックス登録済み・HTTPS OK）**。
- 既にインデックス済みの健全ページへ再リクエストするのは日次クォータ（〜10件/日）の
  無駄であり価値ゼロのため、**index 登録リクエストは発行しない**（verify-before-act）。
- 未登録の健全ハブを能動的にプッシュする場合は「検出 - インデックス未登録(737)」
  バケットの URL 列挙が前提。対象 URL リストが確定すれば次回個別リクエスト可能。
