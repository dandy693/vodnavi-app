# 蓄積データの定期全件走査（設計）— 第28便タスクC

**作成 2026-08-13 17:30 JST / CTO / 設計の提示まで。実装は次便。**

## 1. 何を解決するのか

**§10 の限界2**: 読み戻し検算は「**書いた直後**」にしか効かない。

実例（第27便で記録）: **UTM の `campaign` 不一致は既に配信された後に発見された**。書き込み時点では検査項目が存在せず、読み戻しても検出できなかった。**過去に書かれたものの棚卸しは、読み戻しとは別の手続きを要する。**

同種の実例がもう1件ある（第28便で検出）: **`ACTRESS_LAST_POSTED` に「存在しない配信」が登録されていた**（未配信ストックの `園田茉莉華` を `2026-08-16` で登録）。**これは Airtable のデータではなくコード側の参照データだが、「一度書いたきり誰も再検査しない値」という点で同じ構造**である。

## 2. 対象

**`posts` テーブル全件**（2026-08-13 時点で **71件** = 投稿済53 + 承認済14 + ストック4 ほか）。

**配信済み・未配信を問わず全件を走査する。** 配信済みを走査する目的は修正ではなく**検出と記録**である（下記 §5）。

## 3. 検査項目 — ガード16件のうち事後検査が可能なもの

**判定基準**: 行に保存されている値だけで検査できるか。外部状態（FANZA の在庫、記事の公開状態）や生成時の文脈を要するものは事後検査できない。

| ガード | 事後検査 | 理由 |
|---|---|---|
| **g1** af_id=006 | **可** | `リンクURL` から読める |
| **g2** 99x 不在 | **可** | `投稿文`+`リンクURL` から読める |
| **g3** リンクが works | **可** | `リンクURL` + `タイプ` から読める |
| **g4** 直リンクに #PR | **可** | 両フィールドから読める |
| **g5** %OFF・クーポン | **可**（ただし **T1改のみ**に適用） | §13 の裁定どおり T3セールへは遡及適用しない |
| **g6** 直リンク1日1件 | **可** | `予約日時` で日別に集計できる |
| **g7** 文字数 | **可** | **最優先**。既知の違反3件（W5-12 331 / W6-02 290 / W6-09 351）を検出できる |
| **g8** 時刻 21:00〜23:00 | **可** | `予約日時` から読める |
| **g9** UTC の Z 終端 | **一部可** | Z 終端の検査は可。**「意図した JST と一致するか」は `intendedJst` が行に保存されていないため事後検査できない** |

### 3-1. ガード以外に追加すべき事後検査（2件）

事後にしか検出できない失敗モードがあるため、走査時のみの項目を加える。

| 項目 | 内容 | 根拠 |
|---|---|---|
| **p1 ポストID 欠落** | `投稿済` かつ `ポストID` が空 | 既に `wflWkFObn153NQjVm` が毎週木 10:05 に検知する。**走査側でも重複して数え、両者の件数が一致することを確認する**（アラートの生存確認を兼ねる） |
| **p2 期限切れの外部情報** | `T3セール` の `投稿文` に含まれる期限日が `予約日時` より前 | セール名・料率・期限が外部依存であることは §13 で T3 を自動化対象外とした理由そのもの。**未配信分に限り検出する意味がある** |

## 4. 頻度と実行方法

- **週次・木曜サイクルに統合**。**10:00 在庫アラート → 10:05 ポストID検知 → その後の CTO 作業の冒頭で走査を実行**する。
- **オートメーションではなくスクリプトとして実装する。** 理由: ①検査ロジックは `x-post-generator.mjs` の `GUARDS` を**そのまま再利用**すべきであり、Airtable の式言語では再実装になる ②再実装は**本番のガードと定義がずれる**（ずれた時点で検査の意味が失われる） ③**git の差分レビュー対象**に載る（§13 の緩和策と同じ理由）。
- 出力は `management/_metrics/<週>/audit-<日時>-posts-full-scan.md` に**毎回追記ではなく新規作成**し、**前回との差分を冒頭に置く**。

## 5. 【重要】過去データの違反を検出した場合の扱い

**配信済みは遡及修正しない（既定方針・CSO裁定 2026-08-13）。検出と記録に留める。**

| ステータス | 違反を検出したときの扱い |
|---|---|
| **`投稿済`（配信済み）** | **修正しない。記録のみ。** 走査レポートに一覧として残す |
| **`承認済`（未配信・予約済み）** | **報告する。修正は CSO の指示を待つ。** 第26便の W6-02 / W6-09 がこの経路（文字数超過を検出 → CSO が短縮版を作成 → CTO が差し替え） |
| **`ストック`（未配信・未予約）** | **報告する。** 承認前なので是正の自由度が最も高い |

**理由**: 配信済みの投稿を後から書き換えても **X 上の投稿は変わらない**（Airtable は記録であって配信内容そのものではない）。**修正すると「配信された内容」と「記録された内容」が食い違い、以後の分析が壊れる。** §13 の「配信済み投稿は遡及修正しない」はこの理由による。

**記録の目的は是正ではなく、①同じ違反の再発をガードで塞げているかの確認 ②失敗モードの母数の把握**である。

### 5-1. 検出済みで「修正しない」ことが確定しているもの

| 項目 | 件数 | 扱い |
|---|---|---|
| **UTM の campaign 不一致** | 既配信分 | **遡及修正しない**（CSO裁定・第24便） |
| **文字数超過**（W5-12 331） | 1件（配信済み） | **遡及修正しない**。W6-02 / W6-09 は**未配信だったため第26便で差し替え済み** |
| **T6TV の「2,200作品」表記** | 配信済み分 | **遡及修正しない**（CSO裁定・第26便）。**未配信16件には 0件**であることを確認済み |

**→ 走査レポートでは、これらを「既知・修正しない」として毎回同じ件数で計上する。件数が増えたときだけ新規の違反である。**

## 6. 実装の見積り

**小**。`x-post-generator.mjs` の `GUARDS` を import し、Airtable から全件取得して各行を post 形状へ写像するアダプタを書くのが本体。**新しい検査ロジックは書かない**（g12 の除外と p1/p2 の追加のみ）。

**留意**: `intendedJst` が行に保存されていないため **g9 は Z 終端の検査のみに縮退する**。**JST 換算の意図一致を事後にも検査したい場合は、書き込み時に `作成メモ` へ意図した JST を残す運用に変える必要がある**（本設計では変更を提案するに留め、実施は CSO 裁定事項とする）。
