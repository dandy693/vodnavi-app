# 第26便 タスクB — ポストIDによる配信検知の設計（**実装は CSO 承認後**）

- 作成: 2026-08-13 CTO / **Airtable の `Run automation` は押していない**

## 背景（実測）

配信の実在を判定できる唯一の機械的手掛かりは **`ポストID` の有無**である。
実測（2026-08-13）で **投稿済53件のうち2件が `ポストID` 未記録**（`W5-12` 8/8・`W5-13` 8/9）。
**既存の「エラー通知」は `ステータス=エラー` を見るため、この2件を検知できない。**
**2026-08-01 の枯渇事故（エラー0件のため原理的に検知できなかった）と同型の構造**である。

## (1) 検知の仕組み

**条件**: `ステータス = 投稿済` **かつ** `ポストID` が空。

| 要素 | 設計 |
|---|---|
| トリガ | **cron（毎週木曜 10:05 JST ＝ 01:05 UTC）**。在庫アラート（10:00）の**5分後** |
| Find records | `ステータス = 投稿済`（`sel8BS7Yhjuq3r8T2`）**かつ** `ポストID` **isEmpty** |
| 条件分岐 | `length(records) > 0` のときのみ通知 |
| アクション | `Send an email` → `moterist.com@gmail.com` |

**なぜ「投稿済」に限るか**: `ストック` / `承認済` は配信前なのでポストIDが無くて当然。**`投稿済` だけが「配信されたはず」の状態**であり、そこにIDが無いことが異常を意味する。

## (2) 在庫アラートへの統合か、別オートメーションか → **別オートメーションを推奨**

| | 統合 | **別オートメーション（推奨）** |
|---|---|---|
| 判定式 | 在庫件数（`< 6`）と配信失敗（`> 0`）は**逆向きの条件**。1つの条件分岐に入らず、分岐を2本持つ構造になる | 各1条件で単純 |
| 通知 | どちらが鳴ったのか件名で区別が要る | **件名で自明** |
| 障害の切り分け | **片方が壊れると両方止まる**（在庫アラートは 8/1 の事故を受けて作られた唯一の砦であり、変更リスクを負わせない） | **独立**。片方が止まってももう片方は動く |
| Run history | 1本に混ざり、どちらの実行か読み取りにくい | 分離して読める |

**根拠**: 在庫アラートは枯渇事故の再発防止として稼働中の唯一の検知手段であり（第18便で項目1〜4 + 受信を実測確認）、**そこへ条件を足すのは既存の砦に変更リスクを持ち込む**。**新設ならば既存を一切触らずに済む。**

**※ 実行時刻を 10:05 とするのは、在庫アラートと同じ木曜の運用サイクルに乗せつつ、Run history 上で実行順が明確になるため。**

## (3) 通知内容の設計

**件名**:
```
【X投稿】配信未確認: 投稿済だが ポストID が無い {N} 件
```

**本文**:
```
「ステータス=投稿済」でありながら ポストID が記録されていない投稿が {N} 件あります。

X への配信が成功していない可能性があります。
※ ポストID が無いこと自体は「Airtable に記録されていない」ことしか意味しません。
   X 上に実在するかは、該当アカウントを目視で確認してください。

対象:
{件名} / 予約日時 {JST} / タイプ {タイプ}
（以下、該当行を列挙）

確認手順:
1. X アカウントで該当日時の投稿が存在するか目視で確認する
2. 存在する場合 … ポストID の書き戻しに失敗しただけ。手動でIDを補うか、記録なしのまま扱う
3. 存在しない場合 … 配信が失敗している。本文の文字数（X の重み付き上限 280）を確認し、
   超過していれば短縮して再投稿の要否を判断する

背景: 2026-08-13 の実測で、投稿済53件のうち2件（W5-12 8/8・W5-13 8/9）が
この状態にありました。うち W5-12 は重み331 で上限280を超過していましたが、
W5-13 は重み98 で上限内であり、文字数以外の失敗要因も存在します（原因は未特定）。

（このメールは毎週木曜 10:05 JST の定期チェックによるものです。0件のときは送信されません。）
```

**設計の要点**: **「ポストIDが無い＝配信失敗」と断定しない文面**にした。実測で言えるのは「記録されていない」ことだけであり、**X 上の実在は目視確認を要する**。§4（捏造禁止）と §10（戻り値は着地の証拠にならない）の双方に整合させる。
