## ガードレール9（**最重要**）の設計を詳述

**本日確定した事実**: `2026-08-01T13:30:00.000Z` = **8/1 22:30 JST**（枯渇事故の時刻と一致）。つまり **Airtable の `予約日時` は UTC 格納**であり、**JST の値をそのまま書くと9時間ずれる**。

**9時間ずれると何が起きるか**: 22:30 JST のつもりで `22:30` を書くと **翌 07:30 JST** に配信される。**在庫アラートの判定（`予約日時 >= daysFromNow(4)`）もずれるため、枯渇を検知できずに事故が再発する。**

**二重検査とする**:

| 層 | 検査 |
|---|---|
| **書き込み前** | 生成した ISO 文字列が **`Z` で終わる**こと（`...T13:30:00.000Z`）。かつ **JST 換算した時刻がガードレール8の範囲（20:45〜24:00）に入る**こと |
| **書き込み後（読み戻し）** | **§10 に従い、書き込んだ行を Airtable から読み戻し**、`予約日時` を JST 換算して**意図した時刻と一致する**ことを検査。不一致なら**その行を削除して中断** |

**§10「ツールの戻り値は着地の証拠にならない」をここに適用する。** 書き込み API が成功を返しても、値がずれていないことの証拠にはならない。

| 手段 | 可否 | 根拠 |
|---|---|---|
| **行レベル（レコード単位）の権限** | **不可** | Airtable の権限モデルは**ベース単位／テーブル単位**が基本。**「このロールは status='ストック' の行しか作れない」に相当する制約は存在しない** |
| **フィールド単位の編集権限** | **一部可（ただし本件には効かない）** | Airtable には field-level の編集権限があるが、**これは UI 上の共同編集者に対する制御**であり、**API トークンには適用されない** |
| **API トークンのスコープ制限** | **可（ただし粒度が粗い）** | Personal Access Token に **`data.records:read` / `data.records:write` / `schema.bases:read`** 等のスコープと**ベース単位のアクセス範囲**を設定できる。**しかし「書ける値」を制限することはできない**。`data.records:write` を与えた時点で**任意のフィールドに任意の値**を書ける |
| **Automation による事後の強制** | **可（ただし事後）** | 「`ステータス` が承認済に変わったら条件を検査して差し戻す」等は書けるが、**事前の禁止ではない**。かつ **Automation 自体を書き換えられれば破れる** |

**→ B2②-b で使った「GRANT を出さない / RLS `with check` / トリガ」に相当する DB 層の保証は、Airtable では得られない。**

## (3) 結論 — **B2②-b と同等の保証は得られない**

**過大主張を避けて正確に述べる**（第15便で「DB が保証できること／できないこと」を切り分けたのと同じ扱い）:

| | **B2②-b（Supabase）** | **X投稿（Airtable）** |
|---|---|---|
| AI が承認済を作れないことの保証 | **DB 層で構造的に不可能**（GRANT なし + RLS `with check` + トリガ3種） | **保証できない** |
| 実際の防御 | 三層（GRANT / RLS / トリガ） | **一層のみ**＝**書き込みスクリプトが `status='ストック'` を固定する** |
| **破られ方** | AI 提案バッチのプロセスが `link_approver` の鍵を持たないため、**スクリプトを書き換えても live に到達できない** | **スクリプトを書き換えれば `承認済` を直接書ける**。トークンのスコープでは防げない |
| 承認の人間性 | **DB では検証できない**（運用構造で担保） | **同上。かつ DB 層の下支えもない** |

**記録すべき帰結**:
1. **X投稿の自動化は、B2②-b と同じ「AI は提案まで」の保証水準を満たさない**
2. 防御は **スクリプト側の1層のみ**であり、**スクリプトの改変で破れる**
3. したがって **スクリプトの変更は git の差分レビュー対象**とし、**`status` を書く箇所を1箇所に限定**して監査可能にする（**これは緩和であって保証ではない**）
4. **在庫アラート（週次・閾値6件）が最後の砦**として機能する。仮に誤って `承認済` が量産されても、**アラートは「承認済が閾値以上あるか」しか見ないため誤投入を検知できない**——**この点も限界として記録する**
