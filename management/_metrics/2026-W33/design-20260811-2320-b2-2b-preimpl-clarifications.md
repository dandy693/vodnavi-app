# (1) `status` 4段階の使い分け → **4段階を維持する。ただし定義を確定する**

## 定義（**この定義を正とする**）

| status | 定義 | 誰が書けるか | 公開面 |
|---|---|---|---|
| **`proposed`** | AI が提案した直後。**`ai_proposer` が INSERT できる唯一の値** | `ai_proposer`（INSERT のみ） | 出ない |
| **`approved`** | **人間が内容を承認した**。内容の正しさは確定したが、**掲出タイミングはまだ決めていない** | `link_approver`（UPDATE） | **出ない** |
| **`live`** | **レンダラの抽出条件に一致する状態**＝掲出中 | `link_approver`（UPDATE） | **出る**（レンダラ実装後） |
| **`retired`** | 撤去済み。**コード revert 不要のロールバック先** | `link_approver`（UPDATE） | 出ない |

**レンダラの抽出条件は `status = 'live'` のみ**とする（`approved` は含めない）。

> **注**: BRIEF_126 §3 には「works詳細 … `internal_links`(rule・**approved**一括)から描画」とあり、§5 には「CSO承認 → CTOが status=**live** UPDATE」とある。**原設計内で表記が揺れている**。本記録で **`live` のみを描画対象**として確定する。

## `approved` と `live` の間に何が起きるか → **「掲出タイミングの決定」だけが起きる。技術的な処理は無い**

レンダラは**リクエスト時に DB を読む**（SSR + ISR）。ビルドやバッチによる「公開処理」は存在しない。
したがって **`approved` → `live` は UPDATE 一発**であり、間に技術的な工程は無い。

## それでも4段階を維持すべき理由（**不要ではない**）

| # | 根拠 |
|---|---|
| **1** | **観測窓の交絡回避に必要**。本プロジェクトは R2（+4週）・β/α（〜9/30）・APCTA と**複数の観測窓を同時に走らせている**。「内容は承認したが、観測窓が閉じるまで掲出しない」という状態が**現に必要**である |
| **2** | **掲出時刻を JST 秒単位で記録する運用**（S4 / B2① / B2②-a と同じ）と整合する。`approved` で溜め、`live` への UPDATE 時刻＝掲出時刻として記録できる |
| **3** | **内容の審査（人間の判断）と掲出の決定（タイミングの判断）を分離できる**。両者は別の判断であり、前者は CSO、後者は観測計画に従う機械的判断 |
| **4** | `approved` が無いと「承認したがまだ出したくない」を表現する場所が `proposed` しかなくなり、**AI の提案と人間の承認済みが区別できなくなる** |

**→ 4段階を維持する。** ただし運用初期は `approved` に長く留めず、**掲出タイミングの制約が無いときは承認と同時に `live` へ進めてよい**（2回の UPDATE を続けて行う）。

## 遷移の制約（**トリガで強制する**）

```
proposed → approved → live → retired
                       ↑        │
                       └────────┘（retired → live の復帰を許すかは下記の未解決論点）
```

- **`proposed → live` の直行は禁止**（承認を飛ばせない）
- **`retired` からの復帰**: 初期実装では**禁止**（`retired` は終端）。復帰が必要なら**新しい行を `proposed` から作り直す**。理由＝監査証跡が単純になり、`approved_at` の意味が曖昧にならない。**復帰を許すべきという判断があれば差し戻されたい**

## 同期方式 → **双方向ではなく、列を分割した一方向2本**

| 流れ | 対象列 | 実行主体 | 頻度 |
|---|---|---|---|
| **Supabase → Airtable** | `ステータス` **以外のすべて** | CTO バッチ | 提案生成の直後 |
| **Airtable → Supabase** | **`ステータス` のみ** | CTO バッチ | 週次 or CTO 起動時 |

**双方向同期にしない理由**: 同一列を双方から書くと衝突解決が必要になり、**どちらが正か決められない状態**が生まれる。**列を分割すれば衝突は構造的に発生しない**。

- **`retired` への遷移も Airtable から**（CSO が「撤去」に変えると次の同期で反映）

**この設計は「人間の入力点を1箇所に限定する」ことが目的**であり、`HUMAN_INTERVENTION_LOG` の分類 C を1種類に保つ。

## 承認操作の実行主体と経路

```
① AI 提案バッチ（CTO ローカル）
   Claude API → JSON → 後段バリデーション6件 → ai_proposer で INSERT（status='proposed'）
   └→ 同バッチが Airtable にも同じ行を作成（ステータス=提案中）

② 人間（CSO）
   Airtable のグリッドで ステータス を「提案中 → 承認済」に変更     ← ★人間の入力点はここだけ

③ 承認同期バッチ（CTO ローカル・週次）
   Airtable を読む → 「承認済」の行を link_approver で UPDATE（status='approved'）

④ 掲出（CTO）
   観測計画に従い link_approver で UPDATE（status='live'）＋ 掲出時刻を JST 秒で台帳記録
```

## **「AI が live を作れない保証」がどこで担保されるか** — 正確に述べる

### DB レベルで**保証できること**

| # | 仕組み | 保証内容 |
|---|---|---|
| 1 | **`ai_proposer` に UPDATE / DELETE の GRANT を出さない** | **status を一切変更できない**（既存行を live にできない） |
| 2 | **RLS ポリシー**（`with check (origin='ai' and status='proposed' and approved_at is null)`） | **INSERT 時点で proposed 以外を作れない** |
| 3 | **トリガ `guard_ai_proposal`** | 万一 `ai_proposer` 以外のロール（例: `service_role`）を使ってしまっても、**`origin='ai'` の行は `proposed` 以外で INSERT できない** |
| 4 | **トリガ `guard_status_transition`**（新規提案） | **`proposed → live` の直行を禁止**。live には必ず `approved` を経由する必要がある |
| 5 | **トリガ `guard_live_requires_approval`** | `live` には `approved_at` が必須 |

**→ 1〜5 により「AI 提案バッチのプロセスが live を作ることは構造的に不可能」。**

### DB レベルで**保証できないこと（明示する）**

**「人間が実際に承認したこと」は DB では検証できない。** `link_approver` の鍵を持つ主体が `approved` を書けば、DB からは人間か機械かを区別できない。

**この部分の担保は運用構造による**:

| 担保 | 内容 |
|---|---|
| **資格情報の分離** | **AI 提案バッチのプロセスには `link_approver` の鍵を渡さない**（`ai_proposer` のみをロードする） |
| **LLM は資格情報を持たない** | **Claude API は「JSON を返す関数」であり、DB のアクターではない**。LLM 出力が SQL になることはなく、**スクリプトがバリデーションしてから `ai_proposer` で INSERT する**。ここが実質的な境界 |
| **承認同期バッチは Airtable の値しか見ない** | `link_approver` を使うバッチは、**Airtable で「承認済」になっている行以外を UPDATE しない**。判断を持たない機械的な写像 |
| **監査証跡** | 遷移順が強制されるため、`live` の行は必ず `approved` を経由した履歴を持つ |

**過大に主張しない**: 「DB が人間の承認を保証する」のではなく、**「AI 提案バッチが live に到達する経路が存在しない」ことを DB が保証し、承認の人間性は資格情報の分離が担保する**、というのが正確な記述である。

### 追加の選択肢（**採否は CSO 裁定**）

`approved_by text not null` 列を追加し、`live` には非 NULL を要求する。**人間性の証明にはならないが、誰の操作かの監査列が増える**。列追加は `editorial_articles` ではなく `internal_links` への変更であり、スコープ内。**指示に無いため本便では提案に留める。**
