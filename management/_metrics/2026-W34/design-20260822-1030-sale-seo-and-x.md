## 2. タスクC X 連動の設計（**実装しない**）

### 2-1. キャンペーン名の自動発見 — **日次 cron に統合できる。追加コールは不要**

**現状の到達点**: `/api/cron/snapshot-prices` は **rank 走査方式**でセール中作品を集めており、**キャンペーン名を定数で持たない**。**`price_history.campaign_title` に名称がそのまま入る。**

- **本番実測（2026-08-22）**: `campaign_title` は `50％OFFキャンペーン` **387件** / `ブランドストア30％OFF` **1件**。**名称の発見は既に cron の副産物として実現している。**
- **したがって「名称自動発見」のための追加実装は不要。** 第92便で整理した案A/B/C のうち、**案A（rank 走査・名称不要）を既に採っている。**

**新セール検知の設計（SQL 1本で足りる）**

```sql
-- 前日に存在せず当日に現れた campaign_title ＝ 新セール
select campaign_title, min(campaign_end) as ends, count(*) as items
  from price_history
 where snapshot_date = <today>
   and campaign_title not in (
       select distinct campaign_title from price_history
        where snapshot_date = <today - 1>)
 group by campaign_title;
```

- **`price_history` は日次スナップショットなので、前日との差分で「新規」「消滅」の両方が取れる。**
- **【但し書き】8/22 は検証で cron を複数回実行したため 420行あり、他日と単純比較できない**（§ 第94便補遺で記録済みのラベル）。**差分検知の初回は 8/23 と 8/24 の比較から始めるのが安全。**

### 2-2. 新セール検知 → T3 原稿材料の自動生成

**設計**: cron が新セールを検知したら、**原稿そのものではなく「材料」を出力**する。

| 材料 | 出所 |
|---|---|
| キャンペーン名 | `campaign_title` |
| 開始 / 終了 | `campaign_end`（開始は API の `date_begin`） |
| 対象件数 | 当日の該当行数 |
| 最大割引率 | `1 - price/list_price` の最大 |
| 代表作品（数件） | 割引率降順・`content_id` で決定的に |

- **【承認フローは現行維持】** 材料 → **CTO が原稿を作る** → **ガード17件** → **`ステータス=ストック`** → **承認・予約は別工程**。**自動投稿・自動承認は行わない**（本便の禁止事項）。
- **【§13 の保留との関係】§13 が T3 自動化を保留した理由は「セール名・料率・期限が外部情報に依存し、誤った料率や期限切れを投稿するリスク」だった。** **API から機械取得すれば、__その理由__は解消する**（名称も期限も割引率も実測値になる）。**ただし保留の解除は CSO 裁定であり、本書は解除を提案しない。** **「材料の生成」は原稿の自動生成ではないため、保留に抵触しない。**

### 2-3. 配信タイミングをセール開始日に寄せる運用案 — **現在の cron では間に合わない**

**実測**: 50％OFFキャンペーンは **2026-08-21 10:10:00 開始 / 08-24 09:59:59 終了**（約3日）。ブランドストア30％OFF は **08-19 00:10 開始 / 08-25 23:59:59 終了**（約7日）。

| 制約 | 実測・実装 |
|---|---|
| **cron の実行時刻** | **06:00 JST（`0 21 * * *` UTC）** |
| ガード `g8` の配信時間帯 | **21:00〜23:00 JST** |
| セールの開始時刻（実測） | **10:10** / **00:10** |

- **10:10 開始のセールは、翌日 06:00 の cron まで検知されない。** **同日夜（21:00）の配信枠には間に合わない。** 最短でも**翌日夜＝約35時間遅れ**。3日間のセールでこれは大きい。
- **選択肢（CTO は決定しない）**:

| 案 | 内容 | 材料 |
|---|---|---|
| **α cron を日2回にする**（例 06:00 と 12:00 JST） | 検知の遅れを最大6時間に縮める | **API コールは16回/実行で軽い**（既存の sitemap 生成は384回/日）。**ただし `price_history` の「1日1作品1行」は保たれるが、当日の総行数は実行回数に依存する**（§ 第94便補遺のラベル）。**日次比較のためには「その日の最終スナップショット」を定義する必要が出る** |
| **β 検知専用の軽い実行を足す** | 書き込みはせず、新 `campaign_title` の有無だけを見る | **`price_history` を汚さない。** ただし**別エンドポイントの追加＝実装が増える** |
| **γ 現状のまま（日次06:00）** | 追加なし | **セール開始から最大約20時間の遅れ。3日セールなら残り2日強で告知できる。** **「速報性」をどこまで求めるかは、__X 経由の流入が実際にあるか__を測ってから決めても遅くない**（現状 T3 の流入は UTM が無く測れない → 2-4） |

### 2-4. `g14` / UTM の保留事項との整合

**実装を読んで確認した事実**:

- **`g14_link_target_by_kind` は `kind` が `T5` / `TG` 以外なら素通りする**（`x-post-generator.mjs:523-524`）。**すなわち T3 のリンク先は現在まったく検査されていない。**
- **したがって `/sale` を T3 のリンク先にしても、ガードは反応しない（＝誤りも検出しない）。** **`/sale` を許可するには、g14 に T3 の分岐を追加する必要がある。**
- **UTM**: `g15` が形式を検査するのは **`kind === "TG"` のときのみ**。**T3 には UTM が無い**（第30便の実測「UTM を持つのは TG の一部のみ」）。**`/sale` への X 流入を GA4 で分離するには T3 への UTM 付与が要る。**

**連動を実施する場合に必要な改修（列挙のみ・実施しない）**

| # | 改修 | 理由 |
|---|---|---|
| 1 | **`g14` に T3 の分岐を追加**し、リンク先を `al.*` 直リンク **または** `https://app.vodnavi.jp/sale` に限定する | 現状は無検査。**許可リストを作らないと、誤ったリンク先が通る** |
| 2 | **T3 に UTM を付与**（`utm_source=x_vodnavi` / `utm_medium=social` / `utm_campaign=sale` / `utm_content=t3{n}`）し、`g15` の検査対象へ含める | **付けないと `/sale` への X 流入を GA4 で分離できない** |
