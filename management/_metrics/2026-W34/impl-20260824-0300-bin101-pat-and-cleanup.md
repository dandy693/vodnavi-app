**CSO 裁定(1)(2) は受領し内容を理解した。そのうえで、次の1点は実施しない。**

## タスクB — 掃除処理の実装（**実装済み・push 保留**）

### B(1) 実装した内容

**402 のときに Airtable へ何も書かれなくなった結果（第100便）、`承認済` のまま `予約日時` が過去のレコードが残る。** クレジット復旧時にそのまま配信され、**意図した枠（21:00〜23:00 JST）の外へ出うる**（トリガ窓 20:45〜23:45 JST の範囲内）。

| 項目 | 内容 |
|---|---|
| 対象 | **`ステータス=承認済` かつ `予約日時` が現在より 45分以上過去**。**`予約日時` を持たない行は対象外**（承認済でも未予約のストックは触らない） |
| 書く値 | **`ステータス = エラー`** + **`エラー詳細 = 期限切れ（自動掃除）: 予約 {JST} から {N}分経過しても 承認済 のままだったため配信対象から外した。X への配信は行われていない。`** |
| 書かない値 | **`予約日時` は消さない**——いつの枠だったかが分からなくなると、後から追えない |
| 実行位置 | **cron 後処理。自動投稿より__先__に走らせる**（取り残しを片付けてから枠を選ばないと、枠選択が「過去の予約で埋まっている」と誤判定しうる） |

**【45分の根拠】** トリガは **15分間隔**（実行は 20:45〜23:45 JST の1日13回・§13-3）。**45分は3回ぶんの実行を見送ってなお `承認済`** という状態。**成功例の実配信は予約時刻の +0.16〜4.21分**（n=9・中央値 約0.7分）なので、**正常な遅れと取り違える余地は無い。**

**【ステータスの選択肢名について】** 指示は「`ステータス=エラー(期限切れ)` に変更し、エラー詳細に理由を記録」。
**`エラー(期限切れ)` という選択肢の実在は確認できていない**（台帳で実在が確認できているのは `承認済` / `ストック` / `投稿済` / `エラー` の4つ）。**存在しない選択肢を書くと 422**（第84便の実測）。
**そこで `ステータス` には `エラー` を書き、「期限切れ」は `エラー詳細` に文言で残す**——指示の後半「エラー詳細に理由を記録」に沿う読み方を採った。**`typecast: false` のため、仮にこの読みが誤りでも静かには通らず必ず 422 で落ちる。**

**【`エラー詳細` だけ列名で書く理由】** `scripts/audit-posts.mjs` が実測しているフィールド ID に **`エラー詳細` が含まれていない**（同スクリプトが読まない列のため）。**ID を知らない列を ID では書けない。** 列名で書くと改名時に壊れるが、**Airtable は未知の列名を 422 で拒否する**ため、**静かに違う列へ書くことはない**。**ID が判明した時点で `FIELD` へ移す。**

### B(2) 【重要】**検知と書き込みをフラグで分けた**

**指示は「変更前に該当しうる既存レコードの有無を読み戻しで確認し、既存に影響する場合は変更せず報告」。**
**同じ実行の中で「確認」と「変更」を両方やると、確認の意味が無い。**

**そこで、検知とログ出力は常に走らせ、書き込みだけを別フラグ `T3_CLEANUP_ENABLED`（既定 OFF）で塞いだ。**

| 段階 | 挙動 |
|---|---|
| 1. PAT 配置後の初回 cron | **候補を `VODNAVI_T3_CLEANUP` タグに出す。書かない。** |
| 2. CSO が候補を確認 | **既存運用のレコードが混ざっていないか判断する** |
| 3. `T3_CLEANUP_ENABLED=1` | 以後は実際に落とす |

- **`T3_AUTO_POST_ENABLED` とは別のフラグである**——**掃除は自動投稿が止まっていても意味を持つ**（402 の取り残しは手動運用でも生じる）。

**【既存レコードへの影響が疑われる具体的な材料】**
**第100便で Make の変数ピッカーに表示されたモジュール1 のサンプルバンドルに、次の行が含まれていた**（**Make が保持する過去実行のサンプルであり、現在の実在は未確認**）:

| 項目 | 値 |
|---|---|
| ID | `rec8ccPuB7JWca8qf` |
| 投稿文 | `接続テスト（後で削除）` |
| タイプ | `リンクなし` |
| **ステータス** | **`承認済`** |
| **予約日時** | **`2026-07-10T15:30:00.000Z`** |
| Created Time | `2026-07-09T12:30:34.000Z` |
| 作成メモ | `工程3テスト用。承認時は予約日時をセットしてステータスを…` |

- **この行が現在も存在するなら、掃除の対象に入る**（予約日時が45分どころか1ヶ月以上過去）。
- **【厳守】Make のサンプル表示は過去実行時のスナップショットであり、現在の実在を示さない。** **PAT が無いため現時点で Airtable を照会できず、実在は確認できていない。**
- **これが「既存に影響する場合は変更せず報告」が実際に必要になりうる具体例である。** **だからこそ書き込みを別フラグにした。**

### B(3) 読み戻し検算（実装済み・4項目）

|---|---|---|

### B(4) **push を保留している理由**

**`vercel.json` の `ignoreCommand` は `app-concierge/` に差分が無いコミットのビルドをスキップする。Dashboard からの Redeploy も同じ判定を通る**（2026-08-22 実測）。
**したがって env を反映させるには `app-concierge/` 配下に差分を含むコミットの push が要る。**

- **指示 B(4)「この実装のデプロイに PAT の env 反映を同乗させること」に従い、`79e7c93` を push していない。**
- **PAT が Vercel に入った後に push する。** そうすれば1回のデプロイで env 反映と掃除処理の投入が同時に済む。
- **本記録（docs）も同時に保留する**——docs だけ先に push すると `79e7c93` も一緒に push されてしまい、PAT 無しでデプロイが走るため。
